# Instruments 操作手册：三种卡顿定位

## 0. 拉取与启动

使用 Mac 终端运行：

    git clone --branch ios-instruments-lab --single-branch https://github.com/huhood/TestHHDemo.git ios-instruments-lab
    cd ios-instruments-lab
    open InstrumentsLab.xcodeproj

Xcode 选中 InstrumentsLab Scheme → 选择真实 iPhone → 按 Command+R。

若遇到签名错误：Target → Signing & Capabilities → 选择自己的 Team；必要时修改 Bundle Identifier。

建议真机实测。模拟器可以学习操作，但不能代表真实 iPhone 的性能。

## 1. 实验 A：首次加载卡顿

**制造问题**：打开 A 页面，第一次进入自动在主线程执行约 450ms CPU 运算。优化版把同样工作移至后台。

**使用工具**：Time Profiler + Hangs（静止界面未必出现 Animation Hitch）。

操作步骤：
1. Xcode 菜单 Product → Profile，或快捷键 Command+I。
2. Instruments 选择 Time Profiler，开始录制。
3. 在手机上从首页打开「实验 A」；观察界面短暂停顿。
4. 停止录制，在时间轴选取打开页面的那一小段时间。
5. 找 Call Tree → Main Thread；可选 Invert Call Tree / Hide System Libraries / Separate by Thread。
6. 搜索 LabCPU.busyWork，观察 CPU 样本及其调用路径。也可以找 signpost：FirstLoadWork。
7. 切换「优化版」，点重新运行，再录制一次。比较 Main Thread 上的 CPU 工作是否减少。

**结论**：CPU 计算本身并非禁止；错误在于把昂贵同步工作放到主线程。

## 2. 实验 B：快速滚动掉帧

**制造问题**：故障版每次 cellForRowAt 配置 Cell 都额外执行约 12ms 同步计算。

**使用工具**：Animation Hitches + Time Profiler。

操作步骤：
1. Product → Profile，选择 Animation Hitches，开始录制。
2. 在手机上进入「实验 B」，故障版快速上下滚动 15～20 秒。
3. 停止录制，点击有 hitch 的时段，记录次数和持续时间。
4. 再用 Time Profiler 录制同样的滚动，筛选 Main Thread。
5. 找 cellForRowAt → LabCPU.busyWork，或标记 CellConfigurationWork。
6. 切换优化版，用同一个设备、相似滚动速度重新测量。

**结论**：不是 2000 条数据天然导致卡顿；真正的原因是每次展示新 Cell 都要重复执行同步计算。

## 3. 实验 C：图片出现时卡顿

**制造问题**：故障版在图片需要显示时，于主线程解码接近原始尺寸的 JPEG；优化版在后台生成小尺寸缩略图并缓存。

**使用工具**：Time Profiler、Animation Hitches、Allocations / Memory。

操作步骤：
1. 进入实验 C，等待页面提示「素材准备完成」。第一次会后台生成离线 JPEG，不算入解码性能对照。
2. 录制故障版并滚动列表；观察占位图变成图片的时刻。
3. Time Profiler 找 ImageDecodeOnMain / oversizedDecodeOnMain；留意 ImageIO、CoreGraphics 函数。
4. Animation Hitches 看掉帧是否与大图处理同时发生。
5. 切到优化版，重复操作；找 ImageDownsampleOffMain（应在后台线程）。
6. 用 Xcode Debug Navigator 的 Memory，或 Instruments Allocations，比较故障版与优化版内存变化。
7. 注意：本实验数据来自本地文件，所以可以排除网络下载带宽因素。

**结论**：图片很小地显示在 UIImageView 上，不代表系统只解码了那一点像素；应按控件点尺寸 × Screen Scale 降采样。

## 4. 读懂两种 Instruments

- Animation Hitches：重点回答「界面什么时候出现了掉帧」。
- Time Profiler：重点回答「CPU 时间究竟消耗在什么函数」。
- Hangs：适合观察主线程长时间无响应，尤其是静止页面。
- Allocations：观察分配和内存变化，不要把所有增长都断定为泄漏。
- OS Signpost：代码埋点只负责标记工作区间，不自动证明它造成卡顿。

Time Profiler 的 Call Tree 常见选项：
- Main Thread：优先查看阻塞 UI 的线程。
- Invert Call Tree：从耗时的底层函数往上找调用者。
- Hide System Libraries：先聚焦自己的代码，必要时关闭查看系统实现。
- Self Weight / Weight：区分函数自身耗时和包含子调用耗时。

## 5. 实验注意事项

- 每次对比尽量用同一台真机、相同温度与电量状态、相似滚动动作。
- 录制区间要短，定位问题时尽量只选取真正卡顿的那几秒。
- 当前项目是教学用故障注入，不能把故障版代码用于真实 App。
- 仓库已做静态语法检查，但此环境不能运行 xcodebuild 或真机验证；遇到编译问题请附完整报错。
- 把实验结果记录在 docs/实验记录.md，之后可用于面试复习。
